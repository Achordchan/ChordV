# 客户端测试版版本号规则（2026-09-26）

## 背景

1.1.10 第一次按测试版发布时，版本号没有带编号，就是 `1.1.10`。之后要在 1.1.10 上继续加功能时，才发现已经装了这个测试版的设备收不到任何后续构建。原因是服务端检查更新、客户端提示更新、Windows 签名更新器都要求“新版本号严格大于本机版本号”，而同为 `1.1.10` 的新构建不满足这个条件，服务端也无法区分同一版本号的不同构建。

## 规则

- **测试版必须带编号**：`1.1.10-beta.2`、`1.1.10-beta.3`……，每发一次测试版就递增一次。
- **正式版不带后缀**：`1.1.10`。
- 比较顺序：`1.1.9` < `1.1.10-beta.2` < `1.1.10-beta.3` < `1.1.10`。
  - 测试用户会依次收到每个新的测试版，正式版发布后自动升到正式版。正式版的代码和最后一个测试版不一样也可以，最终以正式版为准。
  - 正式用户从 `1.1.9` 直接升到 `1.1.10`，版本号不跳。
- 版本号只在正式版发布之后才前进到下一个补丁号（1.1.11）。

服务端在建发布、改通道、发布时都会校验这条规则。后台发布页选“测试版”时，版本号必须带编号；选“正式版”时，版本号不能带后缀。

## 转正方式

带编号的测试版**不能原样转为正式版**：安装包里写死了自己的版本号（例如 `1.1.10-beta.3`），原样转正会让正式用户看到带 beta 编号的版本。

验证通过后，按下面的步骤发正式版：

1. 把仓库里的客户端版本号改成不带后缀的正式版本号（例如 `1.1.10`）。需要同步修改的位置以 `apps/desktop/scripts/check-version-consistency.mjs` 为准，另外还有 `Cargo.toml`、`Cargo.lock`、两个 tauri 配置里的窗口标题，以及 `release-desktop.yml` 的默认值。
2. 用 `release-desktop.yml` 以该版本号构建。
3. 在后台发布中心新建正式版并发布。

“转为正式版”按钮只对历史上不带编号的测试版保留。

## 遗留情况

2026-09-26 发布的不带编号的 `1.1.10` 测试版，已经装上的设备不会自动收到 `1.1.10-beta.N`，也不会收到之后的正式版 `1.1.10`，需要手动下载安装一次。该测试版发布需在后台撤回，避免更多设备装上它。
