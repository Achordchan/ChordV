# 客户端构建号（2026-09-27）

> **日常发版不用构建号。** 测试版有问题就升补丁号再发测试版（1.1.10 → 1.1.11 → …），哪个版本没问题就在后台“转为正式版”；正式用户直接升到该版本，中间号码只作为测试版存在过。后台每次只需新建一条发布记录。
>
> 构建号只作备用：仅在确实需要给同一个版本号换安装包时（例如包刚发出就发现打错、且尚无人需要升号）才按下文“同版本换包”操作。

## 规则（不变的部分）

- 安装包只有一种，版本号是普通的 `1.1.10`，不带任何后缀；用户看到的版本号不变。
- 测试版还是正式版，只由后台发布中心选择。同一个安装包先发布为测试版给内测用户，验证后在后台“转为正式版”，原样推给所有人。
- 1.1.9 用户直接升级到 1.1.10，不跳号。
- 不认识构建号的旧客户端，行为和以前完全一样。

## 构建号解决什么

同一个版本号可能要发不止一个安装包（例如内测发现问题，修好后还是 1.1.10）。以前服务端、客户端、Windows 更新器都要求新版本号严格大于本机，第二个包送不到已经装了第一个包的设备。

现在每个安装包都有一个递增的构建号：

- CI（`release-desktop.yml`）把 `github.run_number` 作为 `CHORDV_BUILD_NUMBER` 写进程序，安装包文件名也带上它：`ChordV_1.1.10_build42.dmg`、`ChordV_1.1.10_build42_x64-setup.exe`。本地打包不设置时，文件名保持原样。
- 后台从安装包文件名（或导入地址）识别构建号，发布中心在安装包旁显示“构建 42”，不需要手填。
- 客户端检查更新时上报本机构建号。判断规则：**版本号更大，或者版本号相同但构建号更大**，就算有新版本。构建号本身不会触发强制更新。
- Windows 更新器改用自定义比较规则，服务端只对上报了构建号的客户端返回 `1.1.10+42` 形式的版本号；安装后同时核对版本号和构建号，才判定为安装成功。
- 更新中心以小字显示“当前版本 1.1.10 · 构建 42”，更新日志中也标注构建号。

## 同版本换包（备用，非日常流程）

1. 用 `release-desktop.yml` 以 `1.1.10` 构建，得到带构建号的安装包（例如构建 42）。
2. 后台发布中心：新建或编辑 1.1.10 发布，填入 GitHub 安装包地址导入，发布为**测试版**。
3. 如需修复：改代码后再次运行 `release-desktop.yml`（版本号仍是 1.1.10，构建号自动变为 43）。在后台把该测试版“撤回为草稿”，把安装包替换成构建 43，再重新发布。已装构建 42 的内测用户会自动更新到 43。
4. 验证通过后点击“转为正式版”：同一个安装包原样推给 1.1.9 用户；已在构建 43 上的内测用户不会被重复提示。

## 限制

- 在本功能之前安装的客户端不会上报构建号，只能按版本号比较，无法自动收到同版本号的新构建，需要手动安装一次。
- 构建号来自安装包文件名。手动改名上传时，请保留 `_buildN` 部分；否则该安装包视为没有构建号，只按版本号比较。
