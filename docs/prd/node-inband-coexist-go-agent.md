# PRD：B1 —— Go Agent 接管既有 3x-ui 的 Xray（不装第二个 Xray）

状态：草案，待评审。未开工，未改代码，未动生产。
日期：2026-09-09
基线：main 最新发布线（R3 已删 xui 轨）。schema 为人工恢复的 R3 之前形态。
修订：2026-09-09 推翻"入站归属"决策，见 §3.1；新增 §5.4 凭据轮换。

## 0. 一句话

节点 VPS 上不再安装第二个 Xray；ChordV 的 Go agent 连上 **3x-ui 已经在跑的那个 Xray** 的本机 gRPC，
注入并维护一个只属于 ChordV 的入站与用户，计量直接读该 Xray 的计数器。3x-ui 面板继续服务它自己的用户，
互不可见、互不干扰。

## 1. 为什么可行（已核验的事实，不是假设）

| 事实 | 证据 |
| --- | --- |
| 3x-ui 与 ChordV 可以同读同一份计数器而不互相偷数 | 3x-ui v3.7.0 `QueryStats{Reset_: false}`，软件层自行算增量；ChordV agent 亦为 `getAllUsersStats(false)`（`xray-adapter.ts:57`） |
| **旧版会清零，必须先升级** | 3x-ui v2.8.10 的 `GetXrayTraffic` 调用 `s.xrayAPI.GetTraffic(true)` —— reset=true |
| 面板的 gRPC 端口可从磁盘读到 | 面板自动生成 `/usr/local/x-ui/bin/config.json`，内含 tag=`api` 的 dokodemo-door 入站 |
| agent 早已参数化，指向别的 Xray 是配置不是重构 | `config.ts:92` `XRAY_API_ADDRESS`（强制 loopback/unix socket）、`config.ts:136` `XRAY_INBOUND_TAG` |
| gRPC 接口比面板 HTTP API 稳定得多 | 它是 xray-core 的 protobuf，3x-ui 自己也依赖它；对比已删的 `XuiService` 1,356 行 + cookie 会话 + 两处 `allowedIPs` 版本兼容 hack |

**前置条件（阻断性）**：三台面板全部升级到 ≥ v3.7.0 并复核 `Reset_` 仍为 false。
当前 DMIT 与搬瓦工顶尖已在 3.x，**CN2-GIA 仍为 2.8.10，未升级前不得接入**，否则流量静默漏计。

## 2. 目标形态

```
VPS 上（已有 3x-ui + 它的 xray）
  ┌─ x-ui 面板 ── 管理它自己的入站/用户（写 bin/config.json）
  │
  └─ xray 进程 ──┬─ 面板自用的入站（磁盘配置，面板所有）
                 ├─ api 入站 (dokodemo-door, 127.0.0.1:apiPort)
                 └─ ChordV 专用入站（管理员在面板里手工建，存于 x-ui 库，面板侧不放用户）
                      └─ 其中的用户：内存态，agent 经 gRPC 增删，面板看不到也删不掉
                          ▲
                   chordv-agent（单个 Go 静态二进制，systemd）
                          ▲ HTTPS
                   ChordV 控制面
```

接入一台节点时需要打开一次 3x-ui 面板（建入站、复制分享链接）；**此后的日常操作全部在 ChordV 后台**。

## 3. 已定决策

| 议题 | 决定 | 理由 |
| --- | --- | --- |
| 入站归属 | **入站归 x-ui：管理员在面板里手工创建一个专供 ChordV 的入站；ChordV 只经 gRPC 增删其中的用户** | 入站存在 x-ui 库里 ⇒ Xray 重启后 x-ui 自动重建，不再易失；端口与 Reality 密钥由 x-ui 生成，天然不冲突；ChordV 用户仍是内存态，面板看不到也删不掉。**此项已推翻初稿，见 §3.1** |
| 存量迁移 | **原地切换，沿用现有 UUID/email，不重发订阅** | 客户端连接配置由服务端实时下发（见 §5.2 前提），换端口/参数对 ChordV 客户端用户无感 |
| agent 语言 | **直接写 Go**，单静态二进制 | 目标 VPS 零运行时依赖；xray protobuf 原生；砍掉隔离 Node 运行时那一整套 |
| 代码基线 | **main（最新发布线）+ 一条新的收敛迁移** | 见 §7：该代码经核验可直接跑在恢复后的生产库上 |

### 3.1 关于"入站归属"的推翻（2026-09-09 决定）

初稿定的是 ChordV 自建 `chordv-in`、经 `AddInbound` 注入内存。**已推翻**，改为入站由管理员在面板里建。
理由按重要性排列：

1. **消掉了"内存态易失"这个 B1 最大的运行时风险。** 注入的入站在 Xray 一重启时整个消失，
   端口不再监听、客户端连接被拒；而存在 x-ui 库里的入站，x-ui 每次启动 Xray 都会从自己的库重新生成，
   **自动回来**。用户仍需 agent reconcile 补回（两种方案一样），但损失范围从"入站+用户"缩到"仅用户"。
2. **两个悬而未决的设计问题同时消失**：端口由 x-ui 分配（它自己知道哪些端口被占，不会冲突）；
   Reality 密钥对由 x-ui 生成，无需 agent 自持私钥。
3. **P2 的工作量大幅减少**：不写 `AddInbound`、不写端口冲突检测、reconcile 范围维持"用户"不变。
   agent 早已参数化的 `config.ts:136` `XRAY_INBOUND_TAG` 即可指向面板建的入站——是配置不是新代码。
4. **agent 实际动用的权限更小**：代码里不再出现 `AddInbound`，只有 AddUser / RemoveUser / QueryStats。
   （注意：这不降低 §6 第一行的风险——能连 api 端口就**仍然能**做任何事，只是我们不做。）

放弃的是初稿那句"端口与 Reality 参数由 ChordV 控制"。实际代价评估后认为可接受：
密钥轮换是多年一次的事，真要换就在面板删掉入站重建、在 ChordV 重新导入即可，不需要自动化。

## 4. B1 带来的简化（不只是省一个 Xray）

原 agent 方案里为了让无特权 agent 能改 root 拥有的 Xray 配置，建了一整套交接机制：
`/var/lib/chordv-xray/requests` + systemd path 单元 + root 拥有的 `xray-apply.js` 助手 +
`/etc/chordv/xray/conf.d/` 三份配置 + `xray run -test` + 原子改名 + 端口 LISTEN 归属校验 + 回滚重启。

**B1 下这些全部不需要** —— 因为 agent 不再写任何 Xray 配置文件：入站由面板持有，用户经 gRPC 注入内存。
`xray-apply.ts`（886 行，agent 里最大的单文件）连同它的助手脚本、path 单元、conf.d 布局一并消失。

## 5. 需要新建/修改的东西

### 5.1 Go agent（新建，移植自现有 3,415 行 Node agent）

保留：注册协议、心跳、命令队列、幂等、计量批次上报、重启检测与 reconcile、凭据与身份绑定不变量。
删除：`xray-apply` 交接链路、Xray 安装、conf.d 配置渲染。
新增：
- **面板 api 端口获取**：install 脚本（root）读 `/usr/local/x-ui/bin/config.json` 的 `api` 入站端口，写入 agent env 文件。agent 本身不需要 root，也不读该文件。
- **入站 tag 校验**：`XRAY_INBOUND_TAG` 指向面板建的那个入站。3x-ui 的 tag 惯例是 `inbound-<端口>`，
  控制面按端口推导为默认值并允许后台覆盖。agent 必须在接入时校验一次，**tag 不匹配要作为明确错误上报，
  不得静默重试** —— 否则用户被加到不存在的入站上，表现是"节点在线、用户已下发、但谁都连不上"，极难排查。
  （校验手段 P2 定，候选：一次性 add/remove 探测用户，或读 StatsService 的入站计数器名。）
  **P2 必测**：对一个不存在的 tag 调 AddUser，Xray 是否返回错误。若它静默成功，则"上报明确错误"这条无从谈起，
  必须改用其他手段确认。
  **更隐蔽的一种错法**：tag 合法但指错了入站（比如指到面板自用的那个）——AddUser 会正常成功，
  ChordV 用户被塞进面板的入站，同时下发给客户端的却是 ChordV 入站的端口与 Reality 参数，结果是连不上
  **且没有任何错误**。因此 tag 必须**由导入链接的端口推导**（`inbound-<端口>`）而非自由填写；
  后台允许手工覆盖，但覆盖时须显著告警。
- 依赖：`modernc.org/sqlite`（纯 Go，CGO_ENABLED=0），xray-core protobuf 直接 import。

**相对初稿不再需要**：`AddInbound` 注入、端口冲突检测、入站级 reconcile。
重启后的 reconcile 范围维持现状的"用户"即可，入站由 x-ui 自己重建。

### 5.2 控制面（改动小）

- `ENSURE_INBOUND` **降级为"校验目标入站可用"**，不再创建任何东西（入站已由面板持有）。
- **粘贴 vless 链接导入连接参数**：后台节点表单接受一条 `vless://` 分享链接，解析出
  端口、`publicKey`、`sni`/`dest`、`shortId`、`flow`、`fingerprint`，链接里的 UUID 丢弃不用
  （每个 ChordV 用户有自己的 UUID）。这是必须的，因为**桌面客户端的连接参数由控制面实时下发**，
  后台不知道这些值就没法告诉客户端连哪里。手工逐字段填写作为兜底保留。
- 节点新增字段：面板 api 端口、入站 tag、上述 Reality 参数、面板版本（探测所得）、共存模式标记。
- 新增预检：接入前校验面板版本 ≥ 3.7.0，不达标拒绝激活并给出升级提示。

**接入一台节点时的面板侧要求（写进安装手册与验收）：**

1. 在 3x-ui 里新建一个**专供 ChordV** 的 VLESS + Reality 入站。
2. **入站的到期时间设为永不、总流量设为不限。** x-ui 在入站级到期或流量耗尽时会**停用整个入站**并重生成配置，
   届时该节点会整体哑掉，而 ChordV 侧只看到"用户连不上"，排查代价极高。计费完全由 ChordV 负责，
   面板侧不得设置任何限制。
3. 复制该入站的 vless 分享链接。新版面板建完入站即可复制；若该版本必须有客户端才给链接，
   则建一个占位客户端（同样不限期不限量）用于取链接，拿到后**不要再动它**。
4. **此后不要在这个入站里增删面板用户。** x-ui 在面板增删客户端时会对该入站做热更新；
   若其实现是"清空再按库重建"，ChordV 的内存态用户会被一次抹掉。
   后果等同于一次 Xray 重启（靠同一套 reconcile 恢复，不丢数据、不丢计费），但没必要招惹。

**§5.2 前提（须确认）**：ChordV 桌面客户端的连接参数是登录后由服务端实时下发的，
因此换端口/Reality 参数对这些用户无感，重连一次即可。
**若存在直接使用 3x-ui 发出的订阅链接的用户，这部分不在"无感"范围内，需单独处理。**

### 5.3 收敛迁移（必须新写）

生产库现状：迁移历史标记 `retire_xui_panel` 已执行，实际 schema 却是恢复后的 R3 之前形态。
新迁移必须：
- **幂等**（`IF EXISTS` / `IF NOT EXISTS`），可在两种 schema 上安全运行；
- **绝不 `DELETE FROM "Node"`**（该语句已消费过一次，节点是人工恢复的）；
- **分两步**：先上线 B1 代码（面板列保留不动），三台节点切换完成并稳定观察后，再单独一条迁移 drop 面板列/表/枚举。

### 5.4 用户凭据轮换（新增，针对客户端被逆向）

**前提认知：藏不住。** 客户端必须持有完整连接参数才能喂给本地 Xray，能连上的客户端手里就一定有足够连上的东西。
混淆只提高门槛，不改变结论。因此防线不是"藏住配置"，而是"**让流出去的配置自己失效**"。

已经成立的部分（架构自带，只需守住）：

- **计量在服务端**：计数器挂在 Xray 上按 email 记。用户换 v2rayN 直连，一样烧自己的额度。
- **UUID 由 ChordV 下发、活在 Xray 内存里、由 agent 增删**：到期或超额时一条 `RemoveUser`，流出的配置当场作废。
- 因此"跳过 ChordV 客户端"换到的只是另一个客户端界面，**不是免费**。

必须守住的红线：

> **任何限制都只能靠服务端删用户来兑现，不得依赖客户端自觉。**
> 诸如"限制 N 台设备""到期后 App 自行断开"这类客户端侧逻辑，逆向后全部失效。

新增措施：**定期轮换 UUID**（周期待定，量级为天）。

- 精准打掉"**长期**免费使用"：流出的静态配置到轮换点即死。ChordV 客户端每次启动重新取配置，用户无感。
- **email 保持不变，只换 UUID。** Xray 的流量计数器按 email 记，email 不动 ⇒ 计量连续、台账不跳变
  （正是 §6 末行"计量基线"要守的东西）。实现上是一次 `RemoveUser` + `AddUser`，成本极低。
- 需要一个**新旧 UUID 重叠的宽限期**，否则长时间离线的客户端跨过轮换点后会先失败一次再取到新配置。

已知且暂不处理：**一个账号多人共用**。共用同一 UUID/email ⇒ 额度共享（烧得更快），
但 VLESS 原生不限并发连接数。若日后观察到滥用，可参照 3x-ui 的做法解析访问日志做 IP 数限制。
**先不做**，等出现实据再评估。

## 6. 必须正视的代价与风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **agent 获得 Xray 完全控制权** | gRPC 无细粒度 ACL：能连 api 端口就能 `RemoveInbound` 面板的入站、经 `RoutingService` 改路由。原方案的 root 助手正是为防这个而存在，B1 放弃了这道防线 | systemd 沙箱化、凭据 0600、控制面侧命令白名单校验。**无法从 Xray 侧限权——这是 B1 的真实安全代价，需明确接受** |
| 内存态**用户**易失 | Xray 重启（面板改配置、面板定时任务、机器重启）清空 ChordV 的全部用户。**入站本身由 x-ui 从库里重建，不受影响**——这是 §3.1 换方案换来的 | 已有的 uptime 回退检测 + 用户全量 reconcile；空窗 = 检测间隔，需实测并定 SLO |
| 客户端被逆向、配置外流 | 用户提取 vless 参数后用第三方客户端长期使用 | 见 §5.4：服务端强制 + UUID 定期轮换。**不可依赖客户端侧限制** |
| 面板停用整个入站 | 入站级到期时间/总流量触发时 x-ui 会停掉该入站，节点整体哑掉且 ChordV 侧无直接信号 | 接入时强制设为不限期不限量（§5.2）；验收项 |
| 面板可能"看到"不认识的用户 | 3.x 的 `processClientTraffic` 会遇到 ChordV 的 email 而在自己 DB 里找不到。**因 §3.1 改为共用面板持有的入站，这条比初稿更容易被触发** | 验收项，见 §8。x-ui 的统计任务是遍历它自己库里的客户逐个查计数器，理论上不会去问 ChordV 的 email——但必须实测确认。若有问题，改用 email 前缀命名空间并重置计量基线 |
| 路由规则被替换 | 3x-ui 调 `AddRule(ShouldAppend: false)` 会整体替换路由 | ChordV 的入站不依赖任何自定义路由，走默认出站 |
| 面板 api 端口变更 | 管理员改面板设置可能换端口 | agent 连不上时上报明确错误，后台显示"面板 API 端口可能已变更" |
| 计量基线 | 切换时用户 email 不变 ⇒ xray 的 `user>>>email>>>traffic` 计数器延续，不从零开始 | 切换流程中不得重置 `trafficSnapshot`；若改 email 则必须 `ensureTrafficSnapshotBaseline(replaceExisting)` |

## 7. 关于"能不能用 0.0.10 的代码"——已核验

**能。** 0.0.10 代码可直接运行在恢复后的生产库上：

1. 恢复回来的 9 个面板列全部可空或有默认值（`panelEnabled` 默认 false、`panelStatus` 默认 offline、
   `panelApiBasePath` 默认 `'/'`），post-R3 的 Prisma Client 插入 `Node` 不会失败；
2. `prisma-schema-probe.ts` 只对**本版本已知的列**构造 `SELECT ... LIMIT 0`，多余的列不在探测范围内，
   启动门禁不会拒绝；
3. `NodeControlMode` 枚举在 main 的 schema 与生产库中一致（四值，含 `xui_primary`）。

**真正的阻断不是 schema，是 0.0.10 没有 xui 轨** —— 三台 `xui_primary` 节点在 0.0.10 下无人下发用户、无人计量。
B1 正是补上这一块：让 direct/agent 轨能在装着 3x-ui 的 VPS 上工作。

`prisma migrate deploy` 在生产上不会有待执行迁移（全部已标记），因此 schema 不会被自动清理，
需靠 §5.3 的收敛迁移显式收口。

## 8. 验收（缺一不可，全部需真实环境证据）

1. **前置**：三台面板升级完成，逐台确认 `Reset_` 为 false（读源码版本 + 实测计数器不清零）。
2. **共存计量**：面板与 ChordV 同时计量 24h，两边数值各自自洽，ChordV 侧无漏计。
3. **面板扰动**：在面板增删改一个**它自己的**入站 → Xray 重启 → ChordV 的入站由 x-ui 自动带回、
   全部用户由 agent 自动恢复；记录空窗时长；计量基线未错乱、未重复入账。
4. **面板账目未被污染**：面板侧不出现异常客户端记录或错误日志。
5. **入站未被面板停用**：确认该入站的到期时间为永不、总流量为不限（§5.2），并在后台可见其状态。
6. **原地切换**：一台节点上的存量用户沿用 UUID/email 切到面板建的这个入站，ChordV 客户端重连即通，
   流量台账连续无跳变。
7. **凭据轮换**（§5.4，可在灰度后补做）：轮换一次 UUID，客户端无感重连；轮换前的旧配置在宽限期后失效；
   **email 未变，流量台账连续无跳变**。
8. **回退**：切换失败可退回该节点的 `xui_primary` 状态，不丢用户资产。
9. 收敛迁移在生产库副本上跑通，且在"已 drop"与"已恢复"两种 schema 上都幂等。

## 9. 分期

- **P0**：面板升级（用户执行）+ 逐台确认 `Reset_: false`。**未完成不得进入 P1。**
- **P1**：Go agent 骨架 + 注册/心跳/命令/计量（协议不变，可与现有控制面对接）。
- **P2**：面板入站接入 —— 建站手册（§5.2）+ 后台 vless 链接导入 + 入站 tag 校验 + 用户级 reconcile 实测。
  UUID 轮换（§5.4）可延后至 P4 之后，不阻断灰度。
- **P3**：单节点灰度，跑满 §8 的 1–4。

  **阻断前提（2026-09-10 补记）**：§5.2 的控制面改造必须先落地。现役控制面仍会下发
  `ENSURE_INBOUND`，并依赖它的成功报告来填充节点的连接参数
  （`agent.service.ts` 的 `applyInboundReport`），还用该命令的 dedupe key 做「未完成
  操作」守卫、用 `expectedInboundAppliedRevision` 做 CAS。Go agent 不再部署入站，
  这条命令必然失败 —— 一台在改造完成前就换上 Go agent 的节点会**在线、健康、
  但谁也服务不了**，正是 `agent-install.controller.ts:314` 那条注释警告的状态。
  顺序只能是：先改控制面（面板入站导入），再切 agent。
- **P4**：三台原地切换（§8.5），稳定观察。
- **P5**：收敛迁移 drop 面板列/表/枚举，版本线收口。

## 10. 尚未决定 / 待确认

- 是否存在直接使用 3x-ui 订阅链接的用户？（决定 §5.2 的"无感"是否成立）
- 空窗恢复的 SLO 目标值。
- UUID 轮换周期与新旧重叠宽限期的具体取值（§5.4）。
- 入站 tag 的校验手段（§5.1 两个候选）。
- **是否要删除「本节点从未记录过」的账号**（B1 新增，2026-09-10；已收窄，见下）。

  Node agent 的 reconcile 末尾会卸载所有「活着但不在期望集合里」的账号。那时入站是
  ChordV 自建自有的，陌生账号只可能是自己的残留，删掉是对的；**B1 下入站由面板创建、
  双方共用，`ListUsers` 会一并返回面板自己的账号**，照搬这一行等于让 ChordV 去删
  面板的用户 —— 一个纯由拓扑变化引入的破坏性跨界动作，代码一个字没改。

  **判据不是 email 命名空间，是本地状态库本身。** 一条 desired-user 记录就是
  「这个账号是我们的」的证据，所以分成两类处理（已实现）：

  | 情况 | 处理 |
  | --- | --- |
  | 活着、不在下发名单里、**但本节点有它的记录** | 卸载。断连期间被吊销的订阅正是长这样，留着就是白送；而随后的 `ApplyConfigSnapshot` 会删掉它的本地记录，之后再没有任何东西能发现它 |
  | 活着、不在下发名单里、**且从未在本节点记录过** | 只记录，不处理。可能属于面板 |

  卸载失败必须让整条命令失败，**不能让快照替换把证据擦掉**。

  **仍待定的只剩第二类**：是否存在一种情形需要连「从未记录过」的账号也一并清理。
  `RemoveUnknownUsers` 开关留在那里，但默认关闭，且只应在能证明该入站不共用时开启。
- **升级回放是执行逻辑的第二份实现**（B1 新增，2026-09-10）。

  P1 的所有权凭据（`provisioned_accounts_v2`）在旧库上是空的，所以 `backfillProvisioned`
  会回放命令日志把它重建出来。而"从命令历史推导状态"与"执行命令"是同一套语义的**两份
  代码**，评审里已经因此抓出三类不一致：不继承缺省的 `controlMode`、不合并只带部分字段的
  payload、不复现 `mergeNewerBindings` 的按 binding 取新。三次都是同一个形状。

  三处都已修好，但**结构性的重复还在**。P2 落地真实 Xray 适配器时值得考虑把两者收敛到
  同一段代码（例如让回放直接复用 processor 的判定函数，而不是在 store 里另写一遍），
  这一族问题会整体消失。此前每加一条新语义，都要记得同步改回放。

- **DMIT 那台的接入顺序**：它现在既是控制面的反代入口，又是待接入的节点。
  agent 拿到的是该机 Xray 的完全控制权（§6 第一行），出事的影响面包含控制面入口本身。
  建议排在最后接、或先在另两台跑满观察期。

**已关闭**（由 §3.1 的方案变更解决）：`chordv-in` 端口策略；Reality 私钥生成位置。
